# Socket.IO Master Challenge — Day 1 to Day 4

## Mission

Build a **real-time multi-room support platform** using Node.js, Express, and Socket.IO.

You have learned Socket.IO events, acknowledgements, rooms, private messaging, namespaces, and server middleware. Combine them into one working system.

**Do not copy a complete solution from the internet or ask for the full code.** Design the event flow, decide what each socket is allowed to do, test multiple clients, and debug your own assumptions.

## Rules

- Use **Node.js + Express + Socket.IO**.
- Test with Postman or EchoAPI's Socket.IO client.
- Use at least **3 simultaneous client connections**. Use 4 for the race-condition test if possible.
- You may consult official documentation for syntax, but design the logic yourself.
- Do not add a database. Store data in memory.
- No frontend is required.
- Do not hardcode socket IDs.
- Every custom event must have a defined payload.
- Invalid requests must not crash the server.

## Scenario: HelpDesk Live

Build a real-time customer-support platform with three roles:

- **Customer:** creates a support ticket, joins its ticket room, sends ticket messages, and receives private replies.
- **Agent:** joins the agent workspace, sees available tickets, claims a ticket, and responds.
- **Admin:** receives system-level events and broadcasts announcements.

Use these mock Authorization header values:

| Role | Authorization header |
|---|---|
| Customer | `Bearer customer-token` |
| Agent | `Bearer agent-token` |
| Admin | `Bearer admin-token` |
| Invalid user | Any other value |

The server must determine the role from the token. **Never trust a role sent in an event payload.**

## Required Features

### 1. Authentication middleware

Implement Socket.IO middleware that reads the `Authorization` header and validates the token.

- Reject missing or invalid tokens.
- Attach the authenticated user's ID and role to `socket.data.user`.
- A rejected client must never reach the normal `connection` handler.
- Log authentication failures without crashing the server.

### 2. Namespaces

Create these namespaces:

- `/customer`
- `/agent`
- `/admin`

Each namespace needs its own connection handler. Apply authentication middleware to **every namespace**. Think carefully about whether middleware on the default namespace automatically protects other namespaces.

Authorization requirements:

- Only customers may use customer actions.
- Only agents may use agent actions.
- Only admins may use admin actions.
- A valid token for the wrong role must not be enough to perform an action.

### 3. Ticket creation and rooms

A customer emits `ticket:create` with a subject and description.

The server must:

- Validate the payload.
- Generate a unique ticket ID on the server.
- Store the ticket in memory.
- Add the customer's socket to a room dedicated to that ticket.
- Notify agents that a new ticket is available.
- Acknowledge success with the ticket ID or return a structured error.

Decide how to handle an empty subject, missing description, or payload that is not an object.

### 4. Agent workspace and ticket claiming

An agent connects and joins the shared `agents` room.

When a ticket is created, connected agents receive `ticket:available`.

An agent emits `ticket:claim` with a ticket ID. The server must:

- Verify that the ticket exists.
- Prevent two agents from claiming the same ticket.
- Store which agent claimed it.
- Add the agent socket to the ticket room only after a successful claim.
- Acknowledge success or a useful error.
- Notify the ticket room that an agent has joined.

**Critical test:** Have two agents attempt to claim the same ticket nearly simultaneously. Exactly one may succeed.

### 5. Ticket messaging

Use `ticket:message` with a ticket ID and message text.

- Only the customer who created the ticket and the agent who claimed it may send messages to that ticket.
- The server must check authorization itself. Knowing a ticket ID must not grant access.
- Sender identity and timestamp must be generated by the server.
- Broadcast accepted messages to the ticket room.
- Acknowledge accepted and rejected messages.
- Reject empty messages.

### 6. Private reply

Implement `ticket:private-reply` so an authorized participant can privately message the other participant.

- Only the ticket's customer and assigned agent may use this event.
- Deliver the message only to the intended recipient, not every socket in the ticket room.
- Do not blindly trust a recipient socket ID supplied by the client.
- Return a clear acknowledgement.
- Test that a third client cannot see the private reply.

### 7. Admin namespace

An admin emits `admin:announce` with announcement text.

- Only an authenticated admin may use it.
- The announcement must reach connected clients in all three application namespaces.
- Do not accidentally emit only to the admin namespace.
- Include a server-generated timestamp and admin identity.
- Reject empty announcements.

Choose an appropriate cross-namespace broadcast design and explain why it reaches the intended clients.

### 8. Disconnect and cleanup

- Decide what happens if an agent disconnects while owning a ticket, and implement that policy.
- If a customer disconnects, preserve the ticket record in memory.
- Do not delete a ticket merely because one socket disconnects.
- Explain how a reconnecting user could recover ticket state, even if you do not implement full recovery.

Document your policy and keep it consistent.

## Event Contract

Create `EVENTS.md` or a section in the README documenting every event with:

- Event name and namespace
- Who may emit it
- Payload shape
- Server-side validation
- Resulting event or acknowledgement
- Which clients receive the result

You must design the exact payload and acknowledgement formats yourself. Do not leave them ambiguous.

## Testing Gauntlet

Use at least **3 simultaneous clients**. Use 4 if possible:

- Client A: customer
- Client B: agent 1
- Client C: agent 2
- Client D: admin

Run every test and record **setup → action → expected result → actual result**.

### Authentication and authorization

- [ ] Valid customer token connects to `/customer`.
- [ ] Invalid token is rejected.
- [ ] Customer token cannot perform agent actions.
- [ ] Agent token cannot perform admin actions.
- [ ] Every namespace enforces authentication.

### Rooms and delivery

- [ ] Two agents receive a new-ticket notification.
- [ ] An unrelated customer does not receive another customer's ticket messages.
- [ ] The customer and assigned agent receive ticket messages.
- [ ] A private reply reaches only its intended recipient.
- [ ] Admin announcement reaches clients in all three namespaces.

### Acknowledgements and validation

- [ ] Valid ticket creation returns a ticket ID.
- [ ] Empty subject or description is rejected.
- [ ] Unknown ticket ID is rejected.
- [ ] Empty message is rejected.
- [ ] Unauthorized users cannot join or message a ticket.
- [ ] Every event expecting an acknowledgement receives one on success and failure.

### Race conditions and disconnects

- [ ] Two agents try to claim the same ticket; exactly one succeeds.
- [ ] The losing agent is not added to the ticket room.
- [ ] An agent disconnects while assigned; the documented policy is applied.
- [ ] Restarting the server has the documented effect on in-memory tickets.

For each test, record the setup, action, expected result, and actual result.

## Constraints That Force You to Think

1. A socket can reconnect with a new socket ID. Socket IDs are not permanent user identities.
2. A client can forge fields such as `role: "admin"` or `senderId: "someone-else"`. Ignore client-provided identity and role fields.
3. A room is a delivery mechanism, **not an authorization system**.
4. A client may send malformed data or emit an event in the wrong namespace.
5. Two agents may attempt to claim the same ticket nearly simultaneously.
6. `io.emit()` in one namespace does not automatically broadcast to every namespace.
7. Acknowledgements must be returned on error paths as well as success paths.
8. Never trust a ticket ID, recipient ID, sender name, role, or timestamp supplied by the client.
